# Smart-Community Infra 工作台修改清单核查报告

核查日期：2026-11-18

> **更新（2026-11-18）：** 本报告列出的问题已按第五节顺序修复，当前功能和实车验证清单见 `robot_ws/infra/README.md`。以下保留修复前的核查结论。
核查范围：`robot_ws/infra/`、`robot_ws/tools/start_infra.sh`、`community_bringup/launch/*.launch`、`community_mission/scripts/mission_node.py` 及相关脚本。
核查方式：阅读代码，并在沙箱里用 FastAPI TestClient 实际调用了部分接口（没有 ROS 环境，所以 ROS 相关结论来自代码阅读）。**本次只做核查，没有修改任何代码。**

结论标记：**需要改** = 清单描述属实，必须修改；**部分需要** = 问题存在，但范围或做法和清单略有不同；**不需要** = 现有代码已满足。

## 一、P0 核查结果

| 序号 | 条目 | 结论 | 核查依据 |
|---|---|---|---|
| 1 | 启动脚本参数解析 | **需要改** | `start_infra.sh` 第 14–15 行用 `PORT="${1:-8000}"`、`BIND="${2:-0.0.0.0}"` 按位置取值。执行 `./start_infra.sh --port 9000` 会得到 `PORT=--port`、`BIND=9000`，最终执行 `roslaunch ... port:=--port`，启动失败。脚本注释写的却是 `[--port 8000] [--bind 0.0.0.0]`。 |
| 2 | Launch 参数传递 | **需要改（最严重）** | `hardware / community / finals / field` 四个 launch 中的 `base_protocol` 都是**无默认值的必填参数**。`config.py` 里给的默认值是 `""`，而 `build_roslaunch_cmd()` 会把空值丢掉，所以命令里根本不带 `base_protocol`，roslaunch 会直接报错退出。前端 `startLaunch()` 每次都发送空的 `{}`，也没有参数编辑界面。**结果是：工作台目前无法启动任何带底盘的 launch。** 另外，后端也没有校验 `base_protocol` 的取值（只能是 `aa_bb` 或 `legacy_11`）。 |
| 3 | Launch 互斥检查 | **需要改** | `launch_manager.start()` 只检查“同名 launch 是否已在运行”，不检查组合冲突。实际的包含关系是：`community`、`finals`、`field` 都包含 hardware、navigation 和 services；`debug_perception` 包含 usb_cam 和 services；`mapping` 与 navigation 同时运行会产生同名的 `ekf_localization` 和 `robot_state_publisher`。同名节点重复启动时，ROS 会把先启动的节点踢掉（例如 `/community_serial` 底盘驱动），这在实车上有风险。 |
| 4 | 急停顺序 | **需要改** | `dashboard.emergency_stop()` 先依次 `manager.stop()` 所有 launch，最后才发零速度，与清单要求的顺序相反。还有三个问题：一是没有取消 move_base 目标（ros_bridge 里没有 `/move_base/cancel` 发布器）；二是 `manager.stop()` 是阻塞调用，单个 launch 最长可阻塞 15 秒，而且在 `async def` 里直接执行，会让整个事件循环卡住，期间所有 WebSocket 和遥控都停止响应；三是前端弹窗写的是“将停止所有 launch”，和新的急停语义不一致。补充：`serial_bridge.close()` 在正常退出时会下发零速度，所以目前不至于完全失控；但如果升级到 SIGTERM 或 SIGKILL，就无法保证会发出零速度。 |
| 5 | ROS 话题名称 | **需要改** | 一是 IMU：`wit_normal_ros.py` 发布的是 `wit/imu`（即 `/wit/imu`），EKF 也使用 `/wit/imu`，而 ros_bridge 订阅的是 `/imu`，总览页会一直显示没有数据。二是全局路径：ros_bridge 订阅的 `/move_base/global_plan` 不存在，全局规划器是 `global_planner/GlobalPlanner`，实际话题是 `/move_base/GlobalPlanner/plan`。局部路径 `/move_base/local_plan` 是正确的，因为 move_base.launch 已经做了 remap。三是 `/odom`：它由 navigation 中的 EKF 输出，只启动 hardware 时只有 `/odom_raw`，建议两个都监控。 |

## 二、P1 核查结果

### 1. ROS 导航模块：全部需要改

| 清单项 | 结论 | 现状 |
|---|---|---|
| OccupancyGrid 缓存 | 需要改 | `_cb_map` 和 `_cb_navigation_map` 只统计频率，代码里只写了 TODO。 |
| 地图 PNG | 需要改 | `/api/nav/map.png` 固定返回一张 100×100 的灰色图，原点和分辨率是写死的。 |
| 实时位姿 | 部分需要 | 后端已经缓存 `/amcl_pose`，并写入 state 快照的 `pose` 字段，但前端没有任何地方显示它。另外 AMCL 只在机器人移动后才发布，静止时位姿不会刷新，建议改为从 TF `map→base_footprint` 读取。 |
| /scan | 需要改 | 目前只统计频率，没有缓存点云，也没有提供接口。 |
| 全局/局部路径 | 需要改 | 全局路径的话题名错误（见 P0-5），两条路径都没有缓存。 |
| Local/Global Costmap | 需要改 | 完全没有订阅。 |
| 2D Pose Estimate / Nav Goal / 遥控 | 部分需要 | 后端接口已经实现：`POST /api/nav/pose_estimate`、`POST /api/nav/goal`、`WS /api/nav/teleop`，包括限速和 500 ms 心跳。**但前端“遥控·地图”页面仍是占位文字，没有任何调用。** |
| 统一 API 路径 | 需要改 | 页面提示和 WORKBENCH.md 写的是 `WS /api/teleop`，实际地址是 `/api/nav/teleop`（实测访问 `/api/teleop` 会直接断开）。`stubs.py` 中的 nav 占位路由虽然被真实路由覆盖，但仍然留在代码里，容易造成混淆。 |

### 2. 相机与视觉识别模块：全部需要改

| 清单项 | 结论 | 现状 |
|---|---|---|
| Preview 接口不匹配 | 需要改 | `recognition_ws` 调用了 `Preview(camera_index=0)`、`.open()`、`.read_frame()`、`.close()`，而 `camera_core.Preview` 只有 `publish / capture / get_frame` 三个方法，构造函数也不接受参数。 |
| 不存在的 Recognizer | 需要改 | 已实测确认：`ImportError: cannot import name 'Recognizer'`，WebSocket 连接后立即报错。 |
| 统一相机采集 | 需要改 | `camera_core` 只支持 DJI 和 Orbbec 两种 USB 相机。默认来源 `ros` 和 `thermal` 都没有实现。**需要注意：** hardware.launch 中的 `usb_cam` 已经占用了 `/dev/video0`，所以车载相机只能通过 ROS 话题获取，不能再用 OpenCV 直接打开同一个设备。ROS 话题采集的写法可以直接复用 `tools/camera_web_preview.py` 和 `tools/detector_preview.py`。 |
| MJPEG 视频流 | 需要改 | `/api/camera/stream.mjpeg` 在死循环里不停输出空帧，`Content-Length: 0` 且没有任何 sleep，连接后会占满 CPU。 |
| 来源切换 | 需要改 | `/api/camera/sources` 返回的是硬编码列表，没有真正切换来源的逻辑。 |
| ONNX 加载与切换 | 部分需要 | `detector_core.ONNXDetector` 和 `TrashPipeline` 本身可以使用（从 tools 复制而来），`/api/camera/detectors` 也能读出 detectors.yaml 中的 7 个检测器。缺少的是“按名称加载并缓存检测器”以及接入视频流。推理是阻塞操作，需要放到线程里执行，不能直接在 async 路由里调用。 |
| Overlay 叠加 | 需要改 | 整个项目没有任何地方调用 `overlay.py`。而且 `draw_boxes()` 要求输入字典 `{"box","label","confidence"}`，检测器输出的却是 `Detection` 命名元组，接入前需要先转换格式。 |
| 快照保存 | 需要改 | `POST /api/camera/snapshot` 只返回一个 placeholder 路径，没有保存任何文件，也没有 `check_writable`。下载不存在的快照时会直接抛出 `FileNotFoundError`，返回 500 而不是 404。 |
| 重复接口 | 建议清理 | 目前同一类功能有多套接口：`stubs.py` 中的 `/api/stream.mjpeg` 和 `/api/detectors`（仍然返回 501），`camera.py` 中的 `/api/camera/*`，`/api/camera/recognition` 和 `/api/camera/perception` 两个 WebSocket（后者是占位），以及 tools 下的两个独立预览脚本。建议按清单的流程只保留一条 `/api/camera/*` 链路。 |

### 3. 巡检任务模块：全部需要改

| 清单项 | 结论 | 现状 |
|---|---|---|
| 巡检状态发布 | 需要改 | `mission_node.py` 中没有任何 Publisher，也没有 `/mission/state` 话题。**另一种做法：** `ResultManager` 每次状态切换都会写 `mission_results.json`，其中包含 `state`、`current_waypoint` 和 `error`。工作台直接读取最新一次运行的这个文件也能拿到真实状态，这样不需要改 mission_node。 |
| /api/mission/state | 需要改 | 它只是一个 WebSocket，连接后发送一次固定的 `IDLE` 就不再推送（GET 请求会返回 404）。state 快照中的 `mission` 字段始终为 `None`。 |
| 单航点任务启动 | 需要改 | `POST /api/mission/single` 只打印一条日志就返回 `ok`，并没有启动任何东西。启动注册表里也没有单独的 `mission` 条目，而 `field.launch` 不支持传入 `single_waypoint`。正确做法是：新增一个 `mission` launch 条目（参数为 `single_waypoint`、`navigation_only`、`obstacle_mode`），并要求 hardware、navigation 和 services 已经在运行。 |
| 完整巡检启动/停止 | 需要改 | 目前只能通过启动或停止 `field`、`finals` 整套 launch 来实现，没有单独的任务启停接口，前端也没有对应页面。 |
| 当前航点/任务类型/结果/错误 | 需要改 | 前端“巡检任务”页面仍是占位文字。 |
| 结果列表和图片/视频查看 | 部分需要 | 后端已有 `/runs`、`/runs/{id}/file` 和 `/runs/{id}/download` 三个接口，但**结果文件名写错了**：代码读取的是 `result.json`，mission_node 实际写入的是 `mission_results.json`，所以 `result` 字段始终为空。前端也没有对应页面。 |
| “仅导航”语义 | 需要改 | 已确认：`navigation_only=true` 时，`task()` 会直接跳过所有任务，包括红绿灯等待、拍照识别和录像。`field.launch` 中的说明却写着 “Skip obstacle detection”，`mission.py` 中写着 “Skip obstacle avoidance”，两处都不准确。另外，`field.launch` 说 `obstacle_mode` 可以设为 `disabled`，但 mission_node 只接受 `blocked` 和 `clear`；如果前端提供 `disabled` 选项，mission 会启动失败。 |

## 三、P1 后端修正核查结果

| 序号 | 条目 | 结论 | 核查依据 |
|---|---|---|---|
| 1 | 日志跨线程通信 | **需要改** | `_pump_output` 运行在普通线程中，却直接对 `asyncio.Queue` 调用 `put_nowait`，这不是线程安全的写法。实测：在后台线程发布一条日志后，等待中的消费者要等到事件循环被其他事件唤醒才能收到，测试中延迟了 5 秒。线上运行时依赖 2 Hz 的状态推送“顺带”唤醒，所以表现为日志延迟和偶发丢失。此外，日志队列只有 8 条，launch 刚启动时日志输出很密集，大部分行会被丢弃。 |
| 2 | 前后端 API 统一 | **需要改** | 汇总上面已列出的问题：`/api/teleop` 实际是 `/api/nav/teleop`；`/api/stream.mjpeg` 和 `/api/detectors` 实际在 `/api/camera/` 下，旧地址仍返回 501；`/api/mission/state` 只有 WebSocket；巡检结果文件名不一致。目前前端只实现了总览页，所以这一项实际上要和前端三个页面的开发一起完成。 |
| 3 | Token 携带 | **需要改（仅在启用 Token 时）** | 前端所有 `fetch` 都没有带 `X-Infra-Token` 请求头，启用 Token 后，启动、停止和急停都会返回 401。所有 WebSocket 都没有做任何校验，**包括 `/api/nav/teleop`，也就是说启用 Token 或只读模式后，仍然可以通过它直接遥控小车。** 如果车上不打算启用 Token，这一项可以暂缓，但只读模式下遥控 WebSocket 仍然可用，这个问题需要修复。 |
| 4 | 巡检记录过滤 | **需要改** | `MISSION_ROOT=~/.ros/community` 下除了 `infra` 目录，还有 services.launch 写入的 `detections/`、`ocr/` 和 recorder 默认的 `videos/` 目录，这些都会被当作巡检记录显示出来。建议只保留包含 `mission_results.json` 的目录。 |

## 四、清单之外但影响使用的问题

下面这些问题会直接影响启动或实车安全，建议并入本轮修改：

1. **启动/停止接口阻塞事件循环。** `POST /api/launch/{name}/stop` 和急停都在 `async def` 中同步执行 `manager.stop()`，最长阻塞 15 秒。在此期间状态推送和遥控 WebSocket 都会停止响应。改为 `def` 路由或使用 `run_in_threadpool` 即可解决。
2. **roscore 未启动时，工作台可能卡在启动阶段。** `server.lifespan` 中会调用 `rospy.init_node()`。用 `run.sh` 或 `python -m infra.server` 直接启动且没有运行 roscore 时，`init_node` 通常会一直等待 master，导致网页打不开。通过 `infra.launch` 启动时，roslaunch 会自动拉起 master，所以不受影响。这一点需要在实车上确认。
3. **ros_bridge 订阅原始图像只为统计频率。** 订阅 `/usb_cam/image_raw` 后每帧都要完整反序列化，在车载 CPU 上开销不小。改成只统计频率的轻量订阅（AnyMsg），或者降低订阅频率即可。
4. **`start_infra.sh` 使用 `set -u`。** 之后执行的 `source /opt/ros/noetic/setup.bash` 在部分环境下会因为未定义变量而失败。建议把 `set -u` 放到 source 之后，或者实测确认没有问题。

## 五、建议修改顺序

1. 先修 P0-2（`base_protocol` 传参与校验）和 P0-1（启动脚本），让工作台能真正启动 launch。
2. 再修 P0-4（急停顺序、取消导航、不阻塞事件循环）和 P0-3（launch 互斥），保证实车安全。
3. 然后修 P0-5 话题名称和 P1 后端修正中的第 1、4 项（工作量小，效果直接）。
4. 最后按导航、相机、巡检的顺序补齐 P1 功能，前端三个页面和 API 地址统一放在同一批完成。
